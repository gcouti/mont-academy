Encontro 07 · Interfaces e Vibe Coding

Da tela que só mostra à tela que edita e confirma

Transforme a consulta do E05 numa interface completa — criar, editar e excluir — e adicione um botão que prepara a confirmação de reunião com o cliente.

O que muda da consulta para a edição

No E05 você fez uma tela que lê as cinco tabelas, com RLS garantindo que cada advisor só vê o que é seu. Hoje essa tela ganha botões de criar, editar e excluir — e editar dado é mais arriscado que ler dado.

OperaçãoRisco que não existia em leituraProteção
CriarRegistro duplicado, campo obrigatório vazioValidação no formulário antes de enviar
EditarSobrescrever um dado certo com um errado, sem perceberFormulário abre com o valor atual preenchido; confirmar antes de salvar
ExcluirApagar um cliente que tem interação, tarefa e posição ligadas a eleConfirmação explícita — nunca um clique só
RLS protege contra outro advisor editar o seu dado — não te protege de você mesmo editar o campo errado. A interface é a sua segunda linha de defesa: confirmação antes de salvar, confirmação antes de excluir.
O princípio do curso continua: o agente mostra o código antes de aplicar; você aprova. Vale também aqui — qualquer alteração de schema ou dado em massa passa pelo mesmo crivo do E05.

Da leitura (E05) ao CRUD completo

Você parte da tela do advisor que já existe. O prompt pede as três operações que faltam — uma de cada vez, não tudo junto.

1
Criar — formulário com os campos obrigatórios de cada tabela (ex.: cliente pede nome; tarefa pede descrição e prazo). Valide antes de enviar.
2
Editar — abre o registro com os valores atuais já preenchidos. Nunca um formulário em branco para editar algo que já existe.
3
Excluir — sempre com uma pergunta de confirmação ("Excluir o cliente X? Isso não apaga as interações e tarefas ligadas a ele."). Nunca um botão que exclui direto.
4
owner_id continua automático — o formulário nunca deixa escolher o owner_id; ele vem de auth.uid(), igual ao E05.

prompt ao agente
Os dados estão no Supabase (o mesmo projeto do E05) — leia e grave de lá, não invente dado de exemplo. Na tela do advisor que já existe, adicione criar, editar e excluir para as cinco tabelas. Regras: (1) o formulário de edição vem preenchido com os valores atuais, lidos do Supabase; (2) excluir sempre pede confirmação explícita, nunca um clique só; (3) owner_id nunca é campo do formulário — continua vindo de auth.uid(); (4) mostre mensagem de sucesso ou erro após cada ação. Mostre o código antes de aplicar e espere minha aprovação.
Reteste o RLS depois de adicionar escrita. O teste de dois usuários do E05 (A insere, B não vê) agora ganha uma segunda parte: B tenta editar ou excluir uma linha de A — e tem que falhar. Ler e escrever são políticas separadas; confirmar uma não confirma a outra.

Uma tela inicial, com o resumo do dia e o botão de confirmação

Em vez de espalhar o botão dentro de cada tabela, ele mora numa tela inicial (home) do advisor: um resumo do dia — quantas reuniões, quantas tarefas vencendo — e, junto de cada reunião, o botão que prepara o rascunho de confirmação.

Regra do curso que não muda aqui: nada gerado por IA vai ao cliente sem você revisar — a mesma do E08/E09. O botão prepara a mensagem; você lê, ajusta se quiser, e manda pelo canal que já usa (WhatsApp, e-mail). Não é um envio automático.

O que a tela inicial faz

1
Ao abrir, busca no Supabase as reuniões de hoje e os próximos dias (tarefa e interacao com data futura) e monta o resumo.
2
Para cada reunião, mostra o botão "Pedir confirmação". Ao clicar, lê cliente, data, horário e local/link do mesmo registro.
3
Gera um rascunho curto e educado pedindo confirmação — só com o que está no registro, nunca inventa horário ou local que falta.
4
Mostra o rascunho na tela com um botão "copiar". Nenhuma chamada a WhatsApp, e-mail ou qualquer API de envio.
5
Registra em interacao que o rascunho foi preparado, com origem = e07-confirmacao-reuniao.
prompt ao agente
Os dados estão no Supabase (o mesmo projeto do E05/E06, já conectado) — leia de lá, não invente dado de exemplo. Crie uma tela inicial (home) para o advisor. Ao abrir, ela busca no Supabase e mostra um resumo do dia: quantas reuniões hoje, quantas tarefas com prazo essa semana, e a lista das próximas reuniões (tarefa ou interacao com data futura, do cliente deste advisor). Em cada reunião da lista, adicione um botão "Pedir confirmação". Ao clicar: monte uma mensagem curta e educada pedindo confirmação de presença, usando só os dados que já estão no registro (cliente, data, horário, local/link). Se faltar algum desses dados, não invente — deixe uma nota "faltou X" no lugar. Mostre o rascunho na tela com um botão "copiar", sem nenhum envio automático. Depois de gerar, registre uma linha em interacao com origem "e07-confirmacao-reuniao". Mostre o código antes de aplicar.
Verificação: o resumo do dia reflete o Supabase, não dado fixo no código · o botão só aparece em reuniões futuras · a mensagem não inventa dado que falta · nada é enviado automaticamente, só copiado · o rascunho fica registrado em interacao com origem.

Duas formas de construir a mesma interface

Até aqui você pediu ao Claude Code para escrever o código da tela, arquivo por arquivo, versionado no git. Existe outro caminho: ferramentas tipo Lovable, que geram a interface a partir de uma descrição e já hospedam o resultado — o "Caminho B" que o PRD já citava desde o E05.

Claude CodeLovable e similares
Onde fica o códigoNo seu repositório git — você lê cada diff antes de aceitarNa plataforma; exportável, mas não é o fluxo padrão
Quem hospedaVocê escolhe (ex. Vercel)A própria plataforma, por padrão
Velocidade do primeiro protótipoMais devagar — você revisa cada passoMais rápido — a plataforma assume mais decisões por você
Controle sobre RLS e segurançaTotal — você vê e aprova cada política antes de rodarDepende da integração — confira antes de confiar
Quando faz sentidoSistema que vai crescer, dado sensível de cliente, você quer entender cada parteProtótipo rápido, validar uma ideia, interface descartável
Se você fez o Caminho B do E05 (Lovable): as regras de lá valem também aqui. O Lovable pode propor migrações no seu Supabase — recuse qualquer migração que remova owner_id, desative RLS, ou mude a chave de deduplicação, mesmo descrita como "melhoria". Leia a migração antes de aprovar, do mesmo jeito que já faz com o Claude Code: ler, propor, executar.
Não é "qual é melhor" — é a mesma régua do espectro de controle (E04): quanto você quer operar versus quanto você delega. Dado de cliente de investimento pede mais controle; um protótipo para validar uma ideia com a diretoria pode pedir velocidade.
