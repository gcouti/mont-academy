Encontro 04 · Git e Versionamento

Git: a fotografia da pasta

Tirar uma foto do seu trabalho, ver o que mudou, voltar atrás e trabalhar em paralelo — sem medo de quebrar nada.

O problema: a pasta com sete versões

Todo mundo já teve esta pasta:

proposta-cliente.docx
proposta-cliente-v2.docx
proposta-cliente-v2-REVISADA.docx
proposta-cliente-final.docx
proposta-cliente-final-ok.docx
proposta-cliente-final-ok-ESSA.docx
proposta-cliente-final-JOAO-alterou.docx
Qual é a versão boa?
O que mudou da quarta para a quinta?
Consegue recuperar a redação que estava na segunda?

Ninguém sabe. Git é a resposta a esse problema — e só isso. Não é ferramenta de programador; é ferramenta de quem tem arquivo que muda.

O que é Git, em uma frase

Git tira uma fotografia da pasta inteira toda vez que você pede, guarda todas as fotografias em ordem, e permite voltar para qualquer uma delas.

Cada fotografia é um commit. Ela guarda três coisas:

O commit guardaPara quê
O estado de todos os arquivosVoltar ao conjunto, não a um arquivo só
Quando foi tirada, e por quemSaber quando algo mudou
Uma mensagem suaSaber por que mudou
git log — a linha do tempo de fotos
● wiki inicial
● adiciona regra de citação no CLAUDE.md
● ingere lâmina do fundo XP
● corrige tom da carta mensal
● ingere ata de 12/11 ← você está aqui

Cada bolinha é um estado completo e recuperável da sua pasta — não uma lista de alterações, mas uma lista de versões inteiras.

"Isso não vai encher meu computador de cópias?" Não. O Git guarda só o que mudou entre uma foto e a outra. Um ano de commits numa pasta de texto ocupa menos que um PDF.

Onde um arquivo pode estar

O modelo mental que confunde todo iniciante. São três lugares na sua máquina — e um quarto, online (o GitHub), que entra no fim.

1 · Pasta de trabalho
onde você e o agente editam de verdade
git add→
2 · Preparação
o que vai entrar na próxima foto
git commit→
3 · Histórico
todas as fotos, em ordem (local)
git push→
4 · GitHub
cópia online das fotos (backup)
editar escolher o que entra bater a foto enviar para a nuvem

E para voltar?

git checkout traz a pasta de trabalho de volta para o estado de uma foto do histórico. É a seta que fecha o ciclo — e a rede de segurança da aula.

Por que existe a preparação, e não é burocracia: você mexeu em cinco arquivos, mas só três formam uma mudança que faz sentido junto. A preparação deixa você escolher o que entra na foto, para que cada commit conte uma história só.

Analogia: a preparação é a mesa onde você junta os documentos antes de tirar a foto. A pasta é o escritório todo; a foto registra só o que está na mesa.

Em dúvida, rode git status. É o comando que responde "onde eu estou?" — o mais importante e o menos ensinado.

Passo a passo — do zero à primeira foto

Fase 1 · começar a fotografar
1
$ git init
"Passe a fotografar esta pasta."
Roda uma vez só, na pasta do curso. A partir daqui o Git acompanha tudo.
2
$ git status
"O que mudou desde a última foto?"
O mais importante da lista. A regra da aula: em dúvida, rode git status.
Fase 2 · a primeira foto
3
$ git add .
"Inclua tudo que mudou na próxima foto."
Coloca os arquivos na mesa (preparação). Pode ser git add arquivo.md para escolher.
4
$ git commit -m "wiki inicial"
"Bata a foto e dê este nome a ela."
A mensagem deve completar: "se eu voltar para esta foto, eu volto para o momento em que…"
5
$ git log
"Me mostre todas as fotos."
Dica: git log --oneline mostra uma por linha.
Fase 3 · errar de propósito e voltar atrás
6
# apague metade de um arquivo da wiki e salve
Vamos destruir trabalho de propósito — para ver a rede funcionar.
7
$ git diff
"Mostre exatamente o que mudou, linha por linha."
git diff
## Perfil do cliente
- Horizonte de aposentadoria; troca de imóvel em 2–3 anos.
- Perfil moderado, prioriza renda.
8
$ git checkout -- perfil-cliente.md
"Volte este arquivo para o estado da última foto."
Abra o arquivo: está inteiro de novo. Esse é o momento em que Git vira rede de segurança.
Com honestidade: git checkout num arquivo descarta o que não foi commitado. O que você apagou e não fotografou, foi. Daí a regra: commit toda vez que algo funciona. Não precisa estar bonito — é ponto de restauração, e só existe rede onde você armou a rede.

Branch: a versão paralela

O problema que resolve: a wiki está boa e você quer testar uma reorganização grande. Se mexer direto e ficar ruim, você estraga o que estava bom.

main é a versão que vale. Branch é o rascunho paralelo. Você troca entre as duas com um comando, e o que acontece numa não afeta a outra.

Os comandos

1
$ git branch experimento
"Crie um rascunho paralelo a partir de agora."
2
$ git checkout experimento # ou: git switch experimento
"Entre no rascunho." Agora o que você muda fica só aqui.
3
$ git checkout main
"Volte para a versão que vale." O que você fez no branch não afeta a main.
Hoje branch é isolamento, não colaboração. Nada de merge, conflito ou pull request — a gente trabalha sozinho por enquanto. Branch volta com consequência concreta no E11: main vira o que está publicado, branch é onde você mexe antes.

Push: levar as fotos para o GitHub

Git ≠ GitHub. Git é o programa que fotografa a pasta — roda na sua máquina, sem internet (foi tudo o que você usou até agora). GitHub é um site onde você guarda uma cópia dessas fotos: backup hoje, e a fonte de onde o site será publicado no E11.

Até aqui, todas as fotos moram só no seu computador. push envia uma cópia para o GitHub.

Uma vez por repositório
1
$ git remote add origin https://github.com/voce/consultor-wiki.git
"Diga onde fica a cópia online."
Você cria o repositório vazio no site do GitHub e cola o endereço dele aqui. origin é só o apelido do "lá".
2
$ git push -u origin main
"Envie as fotos da main para o GitHub."
O -u só na primeira vez; depois basta git push.
No dia a dia
3
$ git push
"Suba as fotos novas." Rode depois de commitar — pense nele como o backup da sua wiki na nuvem.
o ciclo completo de um dia
$ git status # o que mudou?
$ git add . # coloca na mesa
$ git commit -m "ingere reunião de 12/11"
$ git push # manda pro GitHub
✓ tudo salvo, localmente e na nuvem
Para o E04 original, push era assunto do E11. Está aqui como adiantamento, para você já ver o ciclo inteiro. Se o foco da aula for só a rede de segurança local, dá para deixar o push para depois — ele não muda nada do que você fez em Git até agora.
